# Spec Template

Use this template when creating a spec issue with the `to-spec` skill. Fill in each section with concise, actionable information.

## Metadata

- **Labels**: `spec`, `ready-for-agent`
- **Work Type**: Epic
- **Milestone**: [Set when known]
- **Project**: [Add to relevant project board when applicable]

## Problem Statement

[One or two paragraphs describing the problem from the user's perspective. What pain point are we addressing? Why does this matter?]

## Goals

[What we want to achieve. Each goal should be specific and measurable.]

## Non-goals

[What we are explicitly NOT trying to achieve. This helps define scope boundaries.]

## Functional Requirements

[The core capabilities the solution must provide. Write as user-focused statements.]

### Primary User Flows
[Describe the main ways users will interact with the system to achieve their goals]

### System Capabilities
[What the system must be able to do to support the user flows]

## Acceptance Criteria

[Specific, testable conditions that must be met for the spec to be considered complete. Each criterion should be clear enough to write tests against.]

### Given/When/Then Format Examples
- Given [context], when [action], then [expected outcome]
- Given [context], when [action], then [expected outcome]

## Risks and Open Questions

### Risks
[Potential problems that could impact the project, along with mitigation strategies]

### Open Questions
[Important decisions that still need to be made, with context on why they matter and what information is needed to decide]

## Validation

[How we will verify that the solution works as intended. This might include specific test scenarios, usability testing approaches, or performance benchmarks.]

[Remember: Professional spec standard - the template must be compact, traceable, and ticket-ready. Do not leave placeholder text in the published issue. Use `TBD` only when the unknown is explicitly accepted as an open question.]
